C++ 课程设计测试记录与测试用例

发布于：2026-04-14  •  阅读时间：8 mins

测试是课程设计中容易被忽视但极其重要的环节。这篇文章汇总了我为 Rolex 职位申请系统编写的全部测试用例，分为两个部分：第一部分围绕系统整体功能设计，覆盖正常逻辑、边界值和异常场景；第二部分聚焦于底层结构体和各模块的单元测试。通过这两套测试，我在开发过程中发现了若干逻辑缺陷，也验证了修复后的代码正确性。

功能测试（正常逻辑）

以下测试用例验证系统在标准输入下能否正确计算分数并输出结果。

测试编号输入数据预期计算逻辑预期输出结果
TC-01学历: B (博士), 年龄: 32, 工龄: 1.5, 笔试: 80, 80, 80, 80, 口试: 40学历分: 100, 年龄分: 70+(32-30)×2=74, 工龄分: 70+(1.5-1)×30=85, 总分: 320+80+100+74+85=659总表中显示总分 659.00，若为第一名则收到录取通知
TC-02学历: U (本科), 年龄: 45, 工龄: 4, 笔试: 60, 60, 60, 60, 口试: 30学历分: 50, 年龄分: 100-(45-40)×2.5=87.5, 工龄分: 100-(4-2)×20=60, 总分: 240+60+50+87.5+60=497.5总表中显示总分 497.50，查询功能能检索到该考生
TC-03学历: M (硕士), 年龄: 52, 工龄: 0.5, 笔试: 70, 70, 70, 70, 口试: 35学历分: 75, 年龄分: 75-(52-50)×1=73, 工龄分: 0 (不足1年), 总分: 280+70+75+73+0=528.0总表中显示总分 528.00，排序位于 TC-01 之后

这三组数据覆盖了三种学历类型、四个年龄段区间和三种工龄情况，能够较全面地验证评分算法的正确性。

异常与逻辑缺陷测试

这部分测试旨在暴露代码中潜在的 bug。实际开发中，正是通过这些测试发现了 Application_Count 函数的逻辑反转问题。

测试编号输入数据潜在问题描述预期/实际行为
TC-12人数: 10Application_Count() 的 while 条件写反Bug: 输入 1-50 的有效数字时，程序判定为”输入错误”并要求重输。修复: 将条件改为 while (n > 50 || n <= 0)
TC-13查询: 输入 “exit”退出功能查询功能正常退出，程序结束
TC-14查询: 不存在的姓名查无此人系统提示”未找到…”，然后允许继续查询
TC-15姓名: 包含空格cin >> name 的输入截断Bug: “Zhang San” 被截断为两个输入，导致后续数据错位。建议: 使用 cin.getline() 处理带空格的字符串
TC-16性别: 输入 ‘X’无效输入程序不会报错，但会将 ‘X’ 存入 sex 字段，后续无处理逻辑

发现的代码问题及修复

在 TC-12 中发现的 Application_Count 函数逻辑错误：

原代码（有 Bug）：

while (n <= 50 && n > 0) { // 条件是"如果n在1-50之间，就报错"，逻辑反了
    cout << "输入错误,请重新输入!" << endl;
    cin >> n;
}

修复后：

while (n > 50 || n <= 0) { // 如果n大于50或者小于等于0，才报错
    cout << "输入错误,请重新输入!" << endl;
    cin >> n;
}

这个 bug 的教训是：循环条件的正反逻辑很容易写反，编写时应该先想清楚”什么情况下需要继续循环”，再写出对应的布尔表达式。

小结

这套测试用例的设计遵循了几个原则：

  1. 分层覆盖：从系统级功能测试到模块级单元测试，确保每个层次都有对应的验证手段
  2. 边界优先：年龄、工龄、人数的临界值是 bug 高发区，边界值测试的投入产出比最高
  3. 缺陷驱动：TC-12 和 TC-15 直接暴露了代码中的逻辑反转和输入截断问题，说明测试不仅是验证工具，更是发现问题的探针
  4. 可复现：每条用例都给出了明确的输入数据和预期结果，便于回归测试

建议在项目中使用 Google Test 等单元测试框架将上述用例自动化，配合 assert 断言确保每次代码修改后都能快速验证正确性。
